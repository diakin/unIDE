# Свой USB-драйвер для отладки ReactOS

Oct 16, 2026 · @Andrei

## Цель и что даёт

Нужен небольшой USB-драйвер, работающий в режиме опроса (без прерываний и без стека ReactOS), который ядро может вызвать в любой момент, в том числе после bug check при отключённых прерываниях и на HIGH\_LEVEL.

Что он позволяет:

- **Сброс лога на флешку без перезагрузки.** После bug check драйвер дописывает кольцевой буфер лога в заранее созданный файл. Не зависит от того, сохраняет ли BIOS память при тёплом сбросе.
- **Минидамп.** Тот же путь записи, но вместо текста пишется дамп (KPROCESSOR\_STATE, стек, список модулей). В ke/bug.c сейчас на этом месте стоит FIXME про запись дампа.
- **Отладочный вывод в реальном времени на другой ПК.** Через xHCI Debug Capability (DbC) USB-порт ноутбука становится аналогом COM-порта. Это закрывает отсутствие COM и LAN на ноутбуках.
- **Диагностика самого USB-стека.** Если usbehci/usbxhci не поднимаются, независимый драйвер позволяет понять, отвечает ли контроллер вообще.

Ограничение: драйвер работает только с конкретными типами контроллеров (EHCI, xHCI), и под каждый ноутбук его поддержку придётся проверять.

## Что уже есть

- **PR #3** (ветка kd-file-log-phase0): сообщения BootPhase 0 сохраняются в статическом буфере 64 КБ и попадают в файловый лог `/DEBUGPORT=FILE`. Ограничение: файл открывается только после IopCreateArcNames/IopMarkBootPartition, поэтому 0x7B в него не попадает.
- **PR #10** (ветка kd-ram-log): `/DEBUGPORT=RAM` пишет лог в зарезервированную физическую память 0x00E00000 (1 МБ). С `RAM:REBOOT` при bug check выполняется тёплая перезагрузка, и freeldr (pcramlog.c) записывает лог в RAMLOG.TXT через INT 13h AH=43h. Зависит от того, что BIOS не очищает память при тёплом сбросе; на железе не проверено.

Точки, к которым подключится свой драйвер:

- `ntoskrnl/kd/kdio.c`: новый провайдер в списке KdProviders рядом с KdpRamLogInit (например, `/DEBUGPORT=USB`).
- `ntoskrnl/ke/bug.c`: место после DbgPrint «Fatal System Error», где сейчас стоит переход на RAM:REBOOT, и FIXME про запись дампа.
- `boot/freeldr/.../pcramlog.c` и `FatEnumFileSectors` в `lib/fs/fat.c`: готовая логика «записать данные в кластеры существующего файла», её можно перенести в драйвер почти без изменений.

## Архитектура: поллинговый драйвер флешки

Первый вариант: запись лога на флешку через EHCI после bug check.

**Слои драйвера (снизу вверх):**

1. **Контроллер EHCI.** Регистры через BAR0 PCI. При bug check контроллер уже занят usbehci, поэтому драйвер останавливает его (Run/Stop=0), делает HCRESET и строит свои структуры с нуля. Вернуть контроллер usbehci не нужно: после записи система всё равно останавливается или перезагружается.
2. **Память для структур контроллера.** QH, qTD и буферы данных должны быть в физически непрерывной памяти с известным адресом. При bug check выделять память нельзя, поэтому берётся зарезервированная область, как для RAM-лога в PR #10 (freeldr помечает LoaderSpecialMemory, ядро мапит её MmNonCached заранее в Phase 1).
3. **Порт и устройство.** Сброс порта, проверка high-speed (иначе порт отдаётся companion-контроллеру, этот случай на первом этапе не поддерживается), SET\_ADDRESS, чтение дескрипторов, SET\_CONFIGURATION. Если флешка стоит за встроенным хабом (rate matching hub на многих чипсетах Intel), нужен ещё минимальный драйвер хаба.
4. **Mass Storage.** Bulk-Only Transport (CBW/CSW) и команды SCSI: INQUIRY, TEST UNIT READY, READ CAPACITY(10), WRITE(10), для надёжности SYNCHRONIZE CACHE.
5. **Файл.** Файловая система не пишется. Как в pcramlog.c, файл создаётся заранее нужного размера, список его секторов вычисляется один раз (в freeldr через FatEnumFileSectors) и передаётся ядру через ту же зарезервированную область. Драйверу остаётся только записать секторы по списку.

**Определение флешки.** freeldr знает только BIOS-номер диска, не USB-порт. Простой способ: драйвер перебирает порты, читает сектор 0 и сравнивает его с MBR, копию которого сохранил freeldr (или с подписью диска).

**Порядок при bug check:** DbgPrint «Fatal System Error» → провайдер USB забирает контроллер → ищет флешку → записывает буфер лога → пишет на экран результат → дальше обычный путь (kdb или синий экран).

**Оценка объёма** (предположение, не измерено): несколько тысяч строк C для EHCI + хаб + BOT/SCSI.

## Вывод в реальном времени: xHCI DbC

xHCI Debug Capability — необязательная часть спецификации xHCI. Контроллер ноутбука представляется другому ПК как USB-устройство с двумя bulk-каналами (вход и выход). Для отладки это то же, что COM-порт, только быстрее.

**Плюсы по сравнению с драйвером флешки:**

- Не нужен стек хоста: нет перечисления устройств, хабов и Mass Storage. Настраиваются регистры DbC, контекст и два кольца передачи.
- Можно включить очень рано (BootPhase 0) и писать всё, что идёт через DbgPrint, а не только после bug check.
- При двусторонней связи по ней можно работать с kdb с другого ПК, как с COM-портом.

**Что нужно и что проверить:**

- Наличие DbC в контроллере конкретного ноутбука. Проверяется по списку Extended Capabilities xHCI (ID 10). На Linux: наличие `/sys/bus/pci/devices/.../dbc` при ядре с CONFIG\_USB\_XHCI\_DBGCAP (не проверено на ваших машинах).
- Кабель USB 3 A-A для отладки (без VBUS). Обычный кабель A-A с соединёнными VBUS может повредить порты.
- Принимающий ПК: Linux с драйвером usb\_debug даёт /dev/ttyUSBx. Для Windows 7 нужен драйвер для самого устройства; можно задать в DbC свои VID/PID и читать через WinUSB/libusb небольшой программой. На Win7 этот вариант не проверялся.
- Конфликт с драйвером xHCI: в ветке releases/0.4.14-vgal-2 его нет (в `drivers/usb` только usbehci, usbohci, usbuhci, usbport и классовые драйверы), поэтому никто другой контроллер не тронет. Если xHCI-драйвер появится, его нужно будет научить не сбрасывать DbC.
- Отдельно: на части чипсетов Intel порты переключаются между EHCI и xHCI регистрами PCI (XUSB2PR, USB3\_PSSEN). Для DbC порт должен быть переключён на xHCI.

**EHCI Debug Port** даёт ту же возможность на старых машинах, но требует отдельного устройства (USB debug device, например Net20DC) и работает только на одном физическом порту, который на ноутбуке может быть не выведен наружу.

## Что проверить на каждом ноутбуке

Эти данные нужны, чтобы выбрать первый ноутбук и понять, какие контроллеры должен поддерживать драйвер.

1. **USB-контроллеры и их PCI ID.** В Windows: Диспетчер устройств → Контроллеры USB → Свойства → Сведения → «ИД оборудования». С Linux live-флешки: `lspci -nn | grep -i usb`. Тип виден по классу: 0c03 с prog-if 20 = EHCI, 30 = xHCI, 00 = UHCI, 10 = OHCI.
2. **К какому контроллеру подключена флешка** в каждом физическом порту. В Linux: `lsusb -t` после подключения в каждый порт. Важно, есть ли между контроллером и флешкой встроенный хаб.
3. **Наличие xHCI DbC.** В Linux: `ls /sys/bus/pci/devices/*/dbc` (только если ядро собрано с CONFIG\_USB\_XHCI\_DBGCAP). Надёжнее — небольшая проверка списка Extended Capabilities прямо из kdb или freeldr, её можно сделать первым шагом.
4. **Сохраняется ли память при тёплом сбросе** (нужно для PR #10). Создать на флешке RAMLOG.TXT (1 МБ), загрузиться в «ReactOS (Screen + RAM log)», в kdb ввести `bugcheck`. После перезагрузки freeldr должен сообщить, что лог сохранён.
5. **Режим BIOS:** Legacy/CSM или UEFI, есть ли пункты «USB Legacy Support» и «xHCI Mode» (Auto/Enabled/Disabled). От них зависит, на каком контроллере окажутся порты при загрузке.

## Этапы и риски

**Этапы:**

1. **Разведка.** Заполнить таблицу выше и проверить PR #10 на железе. Добавить в kdb команду, которая печатает USB-контроллеры, их BAR и список xHCI Extended Capabilities — это заодно проверит доступ к регистрам из аварийного контекста.
2. **xHCI DbC, только вывод.** Провайдер `/DEBUGPORT=USBDBC` в kdio.c, инициализация в BootPhase 0, приём на другом ПК. Если на ваших ноутбуках DbC есть, этот вариант проще и полезнее флешки, поэтому его стоит делать первым.
3. **DbC в обе стороны:** ввод для kdb с другого ПК.
4. **Флешка через EHCI** на одном ноутбуке: запись лога после bug check в заранее созданный файл. Нужен тем, где DbC нет.
5. **Минидамп** через тот же путь записи.
6. По необходимости: флешка через xHCI (для ноутбуков без EHCI).

Порядок 2 и 4 зависит от результатов этапа 1.

**Риски:**

- Особенности конкретных контроллеров и флешек (quirks): тайминги сброса порта, флешки, не отвечающие на часть SCSI-команд. Решается перебором флешек и отладкой на каждом ноутбуке.
- При bug check контроллер может быть в любом состоянии, в том числе посреди DMA. Полный сброс контроллера перед использованием обязателен.
- Для флешки: запись в обход FAT-драйвера безопасна только в заранее выделенные кластеры. Если система успела записать на флешку свои данные, их кэш не сброшен, и после аварии понадобится chkdsk.
- Объём работы: по оценке, несколько недель на флешку через EHCI; DbC заметно меньше. Это предположение, основанное на составе слоёв, а не на опыте.
- Готовые поллинговые реализации для сравнения: SeaBIOS (usb-ehci.c, usb-msc.c) и модуль xhci-dbc в Linux. Их состав и совместимость лицензий с GPL-2.0 ReactOS я не проверял; использовать их как справку, не копировать без проверки.
