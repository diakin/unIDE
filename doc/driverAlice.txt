Архитектура: почему «опрос без стека и прерываний» — это правильно
В момент bug check:

прерывания могут быть отключены;
планировщик не работает;
любые блокировки (спинлоки, мьютексы) опасны;
стек может быть в плохом состоянии (особенно если падение было из‑за переполнения стека).
Поэтому режим опроса (polling) с фиксированным буфером в заранее выделенной памяти — единственный надёжный вариант.

Что понадобится на уровне кода
1. Фиксированный кольцевой буфер в статической памяти
Не используй ExAllocatePool и подобные аллокаторы — они могут не работать в момент падения. Выделяй буфер статически в секции .data или .bss:

VOID LogWrite(const UCHAR *Data, ULONG Length) {
    ULONG i;
    for (i = 0; i < Length; i++) {
        LogBuffer[LogHead] = Data[i];
        LogHead = (LogHead + 1) % LOG_BUFFER_SIZE;
        if (LogHead == LogTail) {
            LogTail = (LogTail + 1) % LOG_BUFFER_SIZE; // сдвиг хвоста, если буфер переполнен
        }
    }
}
Никаких спинлоков: в HIGH_LEVEL они могут привести к deadlock’у или зависанию.

2. Прямой доступ к USB-контроллеру (UHCI/OHCI/EHCI)
Для отладочного драйвера проще всего ориентироваться на EHCI (USB 2.0) — он наиболее предсказуем и хорошо документирован. Тебе нужно:

найти EHCI‑контроллер через PCI;
прочитать/записать регистры EHCI напрямую (MMIO);
инициализировать базовый дескриптор и очередь передачи (TD/QTD) вручную;
выполнять транзакции в режиме опроса (без прерываний).
Ключевые шаги:

PCI enumeration: найти устройство по классу/вендору, получить BAR (MMIO).
Инициализация EHCI: сброс контроллера, настройка CAPLENGTH, установка RUN/WAIT.
Настройка QH и QTD: создать статические структуры в заранее выделенной памяти.
Poll-цикл: периодически проверять статус QTD, ждать завершения транзакции.
Важно: не использу стек ядра для этих операций. Все структуры должны быть статическими или в заранее выделенном пуле.

3. Запись на флешку: упрощённый путь
Для отладки не обязательно реализовывать полноценный FAT. Можно:

заранее создать на флешке файл фиксированного размера (например, 1 МБ) и запомнить его смещение (LBA);
писать прямо в этот диапазон секторов (512 байт/сектор) через EHCI bulk‑транзакцию.
Это сильно упрощает драйвер: не нужно парсить FAT, обрабатывать длинные имена и т. п.

Важные ограничения и риски
HIGH_LEVEL IRQL: в этом режиме нельзя вызывать почти ничего из ядра. Только прямые MMIO, простые циклы, статические данные.
Отсутствие прерываний: драйвер не должен зависеть от них. Все операции — через опрос статуса.
Стек: не полагайся на большой стек. Лучше вообще избегать рекурсии и глубоких вызовов.
Консистентность данных: если падение произошло посередине записи, файл может быть повреждён. Поэтому полезно писать дампы «порциями» и добавлять контрольные суммы.
Как это встроить в ReactOS
В ReactOS уже есть базовая поддержка USB, но для отладочного режима лучше сделать отдельный «минималистичный» драйвер, который:

регистрируется как boot-start driver;
инициализируется на раннем этапе загрузки;
предоставляет экспортируемые функции для ядра (например, UsbDebugWriteLog, UsbDebugSaveMiniDump).
Эти функции можно вызывать прямо из ke/bug.c в момент bug check.

Практические советы
Тестируй на виртуальной машине (VirtualBox/QEMU) с пробросом USB. Это позволит быстро проверять работу драйвера без риска для железа.
Используй статические структуры: все очереди, дескрипторы, буферы — в статической памяти.
Не полагайся на драйверы файловой системы: пиши напрямую в секторы.
Добавь простую контрольную сумму (CRC32) для каждого блока данных — это поможет понять, цел ли дамп.
Веди лог в текстовом формате: так проще анализировать данные после перезагрузки.
