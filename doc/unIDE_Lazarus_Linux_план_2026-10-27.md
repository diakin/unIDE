### Ядро редактора

Редактор — окно RichEdit 4.1 (msftedit.dll, класс RICHEDIT50W).

Уже своё (RichEdit этого не делает):
- весь кадр: текст, подсветка, выделение, направляющие, линия правого поля — `PaintDoubleBuffered` → `HighlightVisibleText`, рисование в буфер, на экран один BitBlt; `WM_PAINT` перехвачен;
- каретка (`XorOwnCaret`, свой таймер), полосы прокрутки (`FVScroll`, `FHScroll`), номера строк.

Остаётся за RichEdit:
- хранение текста; позиции — сообщениями `EM_LINEINDEX`, `EM_LINEFROMCHAR`, `EM_GETLINE`;
- правка: `NewRichEditProc` перехватывает `WM_CHAR`, `WM_KEYDOWN`, `WM_PASTE`, `WM_CUT`, мышь, но вставку и удаление выполняет RichEdit (`EM_REPLACESEL`);
- выделение (`EM_EXGETSEL` / `EM_EXSETSEL`), координаты мыши → позиция (`EM_CHARFROMPOS`), положение прокрутки;
- Undo/Redo — своего стека нет, работают `EM_UNDO` / `EM_REDO` / `EM_CANUNDO`;
- буфер обмена, IME;
- окна логов (CompLogEdit, ErrLogEdit, LogEdit, RuntimeLog) — тоже TRichEdit, с цветом.

Конвейер подсветки байтовый: текст в редакторе — ANSI (CP1251), 1 байт = 1 символ; файлы UTF-8 переводятся в ANSI при открытии и обратно при сохранении (комментарий «Поддержка UTF-8» в Unit1).

Шрифт редактора — только моноширинный (`fdFixedPitchOnly`, Unit2.pas). Отрисовка на это пока не опирается: ширины меряются по символам (`GetTextExtentExPoint`) и хранятся в кэше `FLineInfo`.

В LCL нет TRichEdit, а сообщения `EM_*` под GTK/Qt не работают. Это главная часть портирования; всё остальное — замены по месту.

### Кодировка исходников

Проверено: модуль в CP1251 с `{$codepage cp1251}` под FPC отдаёт строковые константы байтами CP1251 без перекодировки. LCL ждёт UTF-8 — кириллица в интерфейсе будет искажена. Для сборки Lazarus исходники должны быть в UTF-8.

Delphi 7 читает UTF-8-литералы как байты ANSI. Одни и те же файлы в UTF-8 для обоих компиляторов не подходят — см. решение Р3.

## 2. Решения

**Р1. Одна кодовая база на переходный период или сразу только Lazarus.**
Рекомендация: переходный период с двумя сборками. Delphi 7 остаётся рабочей сборкой, пока сборка Lazarus под Windows не догонит её по возможностям. Общие модули компилируются обоими (`{$IFDEF FPC}` там, где нужно). После выравнивания Delphi-сборка замораживается — для этого уже есть ветка Delphi7.

**Р2. Ядро редактора — РЕШЕНО (2026-10-28): свой элемент, без SynEdit.**

Основания: отрисовка, каретка и прокрутка уже свои; шрифт только моноширинный; чужой редактор не нужен — свой полностью под контролем. SynEdit потребовал бы переписать готовую отрисовку под его модель. Свой элемент оставляет её и добавляет то, что сейчас делает RichEdit: буфер текста, правку, выделение, отмену, буфер обмена. Устройство — раздел 3.

Следствие: свой редактор делается и проверяется ещё в Delphi 7 (этап 0.7). В Lazarus он переходит готовым, без промежуточного варианта с RICHEDIT50W.

**Р3. Кодировка исходников на переходный период.**
Рекомендация: в репозитории файлы остаются в CP1251 (Delphi 7 собирает как сейчас). Сборка Lazarus идёт через шаг подготовки: копия исходников, перекодированная в UTF-8, в папку сборки. После отказа от Delphi 7 файлы переводятся в UTF-8 один раз, и правило «исходники в CP1251» отменяется.

**Р4. Виджетсет Linux.**
Рекомендация: gtk2 для начала — он стоит по умолчанию с Lazarus для Linux. Ui* рисуют себя сами, поэтому разница с Qt5/Qt6 для них небольшая; Qt5 проверить позже как вариант.

**Р5. Где жить настройкам под Linux.**
Сейчас editor.ini лежит рядом с exe, папка переносится на флешке. Под Linux это сохраняется, если папка программы доступна на запись (не /usr). Рекомендация: оставить как есть — переносная папка; запасной путь `~/.config/unide/`, только если папка программы только для чтения.

## 3. Свой редактор: устройство

### 3.1. Два модуля

Основа буфера уже есть: `TFarEditor` в FarEdit.pas — редактор F4 в unIDE FAR и uniFAR (коммит 5afe27a). Он без окна, собирается Delphi 7 и FPC и умеет: строки WideString, позиция строка/символ, каретка, выделение, откат и повтор группами (набор подряд — одна правка), чтение и запись файлов с определением кодировки (BOM UTF-8 / UTF-16, UTF-8 без BOM, ANSI) и сохранением переводов строк, ленивое состояние подсветки по строкам (SchemeLine), поиск. Тесты модели в FPC есть.

EdBuffer — это TFarEditor, вынесенный в общий класс для обоих редакторов (FAR и основного), с добавками из списка ниже. Чего в TFarEditor нет: таблицы начал строк для сквозного индекса, события изменения для закладок и отметок, единой операции `Replace`, версии текста, нескольких представлений на один буфер.

- **EdBuffer.pas** — текст и правка, без VCL/LCL (как ObjParse: собирается и Delphi 7, и FPC).
  - Строки — массив строк, без символов конца строки; признак CRLF/LF файла хранится отдельно и пишется при сохранении как был.
  - Таблица начал строк (сквозной индекс первого символа каждой строки) — для перевода «индекс ↔ строка/колонка», обновляется от места правки, не целиком.
  - Одна операция правки: `Replace(Start, Len, NewText)`. Вставка, удаление, ввод символа, вставка из буфера, замена, форматирование — через неё.
  - Отмена/повтор: стек записей {место, старый текст, новый текст, выделение до и после}. Группировка: ввод подряд — одна запись до паузы, перемещения каретки или смены типа (ввод / удаление); вставка, «заменить всё», форматирование — одна запись. Отмена восстанавливает и выделение. Глубина — в настройках.
  - Версия текста (сейчас `FTextVer`) и событие изменения {первая строка, было строк, стало строк}. По нему сдвигаются закладки, точки останова, отметки строк, кэш строк, список подпрограмм.
  - `Modified` — сравнение с версией на момент сохранения: отмена до сохранённого состояния снимает признак.
  - Длина строки не ограничена (сейчас RichEdit 4.1 выбран из-за строк длиннее 3071 символа).

- **EdView.pas** — элемент на `TCustomControl` (линия Ui*).
  - Отрисовка — перенос `HighlightVisibleText` / `PaintDoubleBuffered`.
  - Каретка, выделение, клавиатура, мышь, колесо, прокрутка, буфер обмена.
  - Несколько EdView на один EdBuffer — так делается разделение окна (SplitPane): обе панели видят один текст без копирования. Текущее правило (правится панель с фокусом, вторая только для чтения) остаётся настройкой; позже можно разрешить правку в обеих.

### 3.2. Модель позиций

- Внутри: строка/колонка.
- Наружу прослойка (этап 0.1) отдаёт и сквозной индекс в модели RichEdit 4.1 (конец строки = 1 символ). Тогда код Unit1, который сейчас считает в этих индексах, переходит без пересчёта; переводить его на строку/колонку можно постепенно.

### 3.3. Моноширинность

- Ячейка символа фиксированной ширины `CharW` (по шрифту). X = (колонка с раскрытыми табуляциями) × CharW; обратно — делением. Кэш ширин `FLineInfo` и замеры `GetTextExtentExPoint` не нужны.
- Вывод — `ExtTextOut` с массивом шагов, где каждый шаг = CharW. Каждый знак стоит в своей ячейке, даже если у жирного или курсивного начертания шрифта ширина знака отличается.
- Табуляции раскрываются самим редактором (вместо `TabbedTextOut`, которого нет в LCL).
- Под Windows и в LCL используются одни и те же вызовы: `ExtTextOut`, `BitBlt`, `CreateCompatibleDC`, `FillRect`, `GetTextMetrics` есть в LCLIntf для всех виджетсетов (проверено по lcl/include/winapih.inc, Lazarus 3.0). Отрисовка переносится почти без правок.

### 3.4. Кодировка текста в буфере

- В буфере — UTF-16 (WideString), как в TFarEditor: 1 элемент = 1 символ = 1 ячейка для всех символов, кроме суррогатных пар.
- Для символов из CP1251 сквозной индекс в UTF-16 совпадает с индексом в нынешней однобайтовой модели. Позиции, которые Unit1 считает сейчас, не меняются.
- Разборщикам и подсветке строка отдаётся в CP1251 (`LineText` прослойки), как сейчас: ObjParse, IncCheck и др. не меняются. Символ вне CP1251 они видят как «?», но в буфере и файле он сохраняется (сейчас при открытии он теряется).
- Lazarus: UTF-16 → UTF-8 только на границах — вывод видимого куска строки, ввод с клавиатуры (`UTF8KeyPress`), буфер обмена. Разборщики редактора с UTF-8 не сталкиваются (снимает часть риска 8.1).

### 3.5. Что пишется заново (сейчас делает RichEdit)

1. Ввод символов, Enter (с отступом — уже есть свой), Backspace, Delete, Tab / Shift+Tab по блоку, режим вставки/замены (Ins).
2. Перемещение: стрелки, Home (умный — к первому непробельному), End, PgUp/PgDn, Ctrl+Home/End, Ctrl+стрелки по словам (символы слова — из схемы .clr).
3. Выделение: Shift+клавиши перемещения, мышь с протяжкой и автопрокруткой, двойной щелчок — слово, тройной — строка, Shift+щелчок. Позже — выделение столбцом (Alt+мышь).
4. Буфер обмена: Ctrl+C/X/V, Ctrl/Shift+Ins, Shift+Del. Windows — CF_UNICODETEXT (в TFarEditor / UnFar уже есть); LCL — `Clipboard.AsText` (UTF-8).

Пункты 1–5 частично уже есть в TFarEditor и TFarView (UnFar): перемещение, выделение клавишами и мышью, буфер обмена, откат. Их поведение сводится к одному для обоих редакторов.
5. Отмена/повтор (3.1).
6. Ввод через IME — не на первом шаге: русская раскладка приходит обычными символами.

Уже своё и только переносится: отрисовка, каретка, прокрутка, номера строк, направляющие, отметки, парные скобки, Code Insight, поиск/замена (через операции буфера), закладки.

### 3.6. Логи и окна только для чтения

- Логи — EdView только для чтения с цветом на строку (или на кусок строки) вместо цветного RTF.
- Окна, которые сейчас получают RTF от SchemeRtf (GitDiffView, просмотр файлов), — EdView только для чтения с подсветкой по схеме; построение RTF не нужно.

### 4.1. Проекты Delphi 7 в Lazarus-сборке

Поддержка проектов Delphi 7 остаётся. Проверено по коду: от того, чем собран сам unIDE, она зависит в разной мере.

**Не зависит, переходит как есть:**
- правка, подсветка, Code Insight, поиск, закладки;
- сборка: dcc32 — внешняя программа, unIDE только запускает её и разбирает вывод;
- переход к ошибке, .dpr / .dof / .cfg, Project Options. DelphiProj и DelphiOpts уже собираются FPC без правок (пробная сборка, раздел 1).

**Только Windows, остаётся в Windows-сборке:**
- отладчик (DbgEngine, DbgSymbols): отладочный API Windows и разбор .map / TD32 от FPC не зависят. Программы Delphi 7 32-разрядные, поэтому Lazarus-сборка unIDE под Windows — тоже i386-win32;
- BplRtti (палитра из установленных .bpl). Пакет грузится как DLL, классы читаются по раскладке VMT/RTTI Delphi 7. Сейчас для этого используются записи из модуля TypInfo, а в FPC он другой: проверено, `tkSet` = 5, `tkClass` = 15, `tkMethod` = 6, `tkLString` = 8 (в Delphi 7: 6, 7, 8, 10). Нужны свои описания записей RTTI Delphi 7 в BplRtti; тогда модуль одинаково работает в обеих сборках.

**Нужно переделать — конструктор форм Delphi, превью, инспектор, новый компонент:**
- Сейчас форма строится из .dfm настоящими контролами VCL (FormDesigner, FormPreview — через TReader). Список свойств и событий берётся из RTTI живых классов (`GetPropList`). Текст нового компонента пишет `WriteComponent` экземпляра VCL (`DsgNewObjectText`): в .dfm попадают умолчания Delphi.
- В Lazarus-сборке классов VCL нет. Одноимённые классы LCL отличаются свойствами и умолчаниями, и `WriteComponent` записал бы в .dfm проекта Delphi значения LCL.
- Решение — описание классов Delphi 7 как данные: для каждого класса палитры (DsgClasses) — свойства, типы, значения перечислений, умолчания, события с сигнатурами, текст `object … end` нового компонента. Файл один раз создаёт Delphi 7-сборка unIDE, у которой настоящие классы есть (шаг 0.8), и он поставляется с Lazarus-сборкой. Тот же путь уже используется для палитры RapidQ (из .inc) и для пакетов (BplRtti).
- Правка свойств остаётся текстовой, как сейчас: `SetPropText` меняет строку `имя = значение` в .dfm, а не записывает форму заново.
- Вид формы в конструкторе — контролами LCL тех же имён (TButton, TEdit, TPanel…) с переносом известных свойств. Классы, которых в LCL нет или которые отличаются, рисуются заглушками, как сейчас компоненты БД. Вид будет близким к Delphi, но не пиксель в пиксель.

**Под Linux:** сборка через Wine (dcc32), конструктор и инспектор — на том же описании классов, отладчика и чтения .bpl нет.

## 8. Риски

8.1. **UTF-8 и индексы.** Разборщики (ObjParse, IncCheck, RqDbgInstr и др.) считают 1 байт = 1 символ. Разборщики получают строку редактора в CP1251 (раздел 3.4), поэтому для текста редактора это не меняется. Но в Lazarus-сборке строковые константы в исходниках становятся UTF-8: сравнение текста буфера (CP1251) с кириллической константой в коде не совпадёт. Такие места найти поиском до этапа 2. Тексты, что приходят не из буфера (вывод компиляторов, имена файлов), — в UTF-8; на границе с буфером нужен явный перевод.
8.2. **Модель позиций.** Unit1 считает позиции так, как их считает RichEdit 4.1 (конец строки — один символ). Прослойка отдаёт те же индексы (раздел 3.2); расхождение проявится в выделении, поиске, переходе к ошибке. Проверяется переключателем 0.7.4 — сравнением с RichEdit на одних файлах.
8.3. **Поведение правки.** Пользователь привык к поведению RichEdit (перемещение по словам, двойной щелчок, отмена). Новое поведение должно совпадать или быть явно лучше; список отличий ведётся во время 0.7.4.
8.4. **Размер Unit1.** 82 тыс. строк в одном модуле: FPC компилирует, но CodeTools Lazarus работают с таким файлом медленно. Продолжение разбиения Unit1 облегчает перенос.
8.5. **Wine.** Delphi 7 и rc.exe под Linux зависят от версии Wine; поведение проверяется на конкретной системе пользователя.
8.6. **Клавиши рабочего стола Linux** (этап 3.4).
8.7. **Две сборки одновременно.** Пока жива Delphi-сборка, каждая правка общего модуля проверяется двумя компиляторами.
8.8. **Кодировка строк под Linux (найдено на шаге 0.7.2).** В FPC под Linux кодировка строк по умолчанию — UTF-8. Схема .clr читается в строки с этой кодировкой, а ClrScheme сравнивает их с константами модуля в CP1251 (заголовок раздела «• »): сравнение перекодирует константу, и разделы схемы не находятся — остаются цвета по умолчанию (ключевые слова и блочные комментарии без цвета). С `DefaultSystemCodePage := 1251` на время чтения схемы разбор верный. Так же ломаются кириллические строки `Format` в интерфейсе. Под Windows (кодировка 1251) этого нет. Решается вместе с Р3 (UTF-8-копия исходников для Lazarus) и явной кодировкой при чтении файлов.
