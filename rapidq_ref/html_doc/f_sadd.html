SADD Function

Not a Rapid-Q keyword: a user function · source: inc/conversion.inc, line 766 · investigated with rc.exe on 2026-10-09

Returns the address of a copy of a string, kept in a memory stream inside the function.

function sadd(InpStr as string) as long
'Returns the memory offset of the string data in the string variable
' use as pointer to the string variable
DIM Mem AS QMemoryStream
Mem.Write InpStr
Mem.Position = 0
sadd=Mem.Pointer
end function

Syntax: Addr& = sadd(string-expression)

The comment in the source says the function returns the address of the string data in the string variable. It does not: the parameter is passed by value, the function writes it into a QMEMORYSTREAM and returns Mem.Pointer, the address of the stream memory. The tests below show what this address is and how long it stays valid.

What the address is

  • It is not the address of the variable: sadd(S1) and VARPTR(S1) differ (test 1, step 1).
  • It stays valid after the function returns: the text is there right after the call and also after 21 other strings and another QMEMORYSTREAM have been created (test 1, steps 2 and 4).
  • It stays valid only until the next call of sadd. Every call writes to the same stream at position 0 and returns the same address, so the address from the previous call now shows the new text (test 1, step 3).
  • The data is not followed by a zero byte. After the bytes of the string the stream memory holds whatever was there before (AAAA[192][6][1], test 2, call 1), and after a shorter string the tail of a longer previous one remains (CCBBBBBB, test 2, call 3). Read exactly LEN(string) bytes from the address; VARPTR$(sadd(s$)), which reads up to a zero byte, can return extra characters.

Why: objects inside a SUB or FUNCTION

An object DIMmed inside a SUB or FUNCTION is created once and keeps its contents between calls; it is not created anew on each call (test 2):

CallTextMem.Size on entryMem.Position on entryLst.ItemCount on entryN on entryText at the address after the call (8 bytes)
1AAAA0000AAAA[192][6][1]
2BBBBBBBB4019BBBBBBBB
3CC8029CCBBBBBB

The address returned by Mem.Pointer was the same in all three calls (17281328), also when the stream grew from 4 to 8 bytes. Mem is a QMEMORYSTREAM, Lst a QSTRINGLIST, N a LONG, all DIMmed in the function.

The numeric variable N behaves differently: on entry it was 0, 9, 9. It does not keep its value (that would be 0, 1, 2), and after the first call it is not 0 either. Where the 9 comes from was not found out.

Using it

  • For the address of the characters of a string variable use VARPTR(s$).
  • If the address from sadd is passed on (for example to a Windows function), it must be used before the next call of sadd, together with the length of the string.

FreeBASIC (unIDE, RqToFb)

Before these tests the translation created the stream anew on every call and freed it on return, so the address pointed to freed memory: right after the call its first bytes were already overwritten. Now an object DIMmed inside a SUB or FUNCTION is translated as Static, and QMEMORYSTREAM keeps its data in a block of a multiple of 8192 bytes, as TMemoryStream of Delphi, so its address does not change while the data fits. The translated tests print the same as rc.exe except the addresses, the bytes after the data in the stream (zeros) and N (0 on every call). Regression test: RqLcl/tofb/tests/localobj.bas; the two test programs: RqLcl/tofb/tests/research/sadd_test.bas, sadd_test2.bas.
