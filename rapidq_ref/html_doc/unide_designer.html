How the unIDE form designer works

Code: FormDesigner.pas (the designer window), RqDesign.pas and RqComponents.pas (Rapid-Q forms), DsgClasses.pas, DsgPalette.pas, DsgForeign.pas, DsgIcons.pas (classes, palette, icons), ObjParse.pas (Objects tree, cache), FormSnapshot.pas (snapshot of a live form), FormPreview.pas (preview in View Form), MenuWizard.pas, DfmMove.pas, and the Dsg..., RqDsg..., RapidQProbe... methods of Unit1.pas.

1. One designer for Delphi and Rapid-Q forms

The designer builds the form from text in the .dfm format with real VCL controls and shows it in a separate window, as the Delphi 7 designer does. Over the form it draws a dot grid, selects a component with a click, moves it with the mouse and resizes it with 8 handles. The handle numbering and the rule which side a handle pulls are taken from RQFormDsg (ShowCarets, MouseResizeObject):

    1   8   7
    2       6
    3   4   5

The handles are drawn inside the frame of the component, not outside: outside they could not be caught at the edge of the form or next to another component.

The designer does not keep the text. It reports a change as the name of the component and lines Name=value; whoever owns the text writes it:

  • for a Delphi form the main window writes the change into the text of the editor tab with the .dfm (only the lines of that object are changed), not to disk: the tab shows the form as modified and nothing reaches the file without Save;
  • for a Rapid-Q form the change goes into the CREATE block of the program (section 6).

The designer has its own undo (Ctrl+Z in its window, or Edit → Undo in its menu). One step covers both files that a change touches (.dfm and .pas). The undo history lives while the form stays open.

2. Editing

  • Grid. Step X and Y, show dots, snap moves and sizes (IDE Options → Designer).
  • Group. Shift+click adds components to a group, as in Delphi. The first one is the main one; alignment and spacing go by it. A group has corner marks instead of handles. A group move or alignment is one undo step.
  • Palette. Click a component on the palette, then click the form: the component is placed into the container under the mouse at the grid point. The name is the first free one (Button1, Button2, ...: free in the .dfm and in the .pas). For a Delphi form the object goes into the .dfm as the last child of its parent, written as Delphi would write it (an instance is created, named, positioned and streamed with WriteComponent, so only non-default values appear), and a field goes into the form class in the .pas. Non-visual components lie on the root of the form and are shown as icons.
  • Double click on a component opens (or creates) its default event handler in the .pas, as in Delphi.
  • Hidden controls (Visible = False in the .dfm or in code) are shown with a red frame.
  • Pages. The designer opens the TPageControl page from ActivePage. When a page is opened (by a click or at load), the OnChange handler of the TPageControl in the .pas is parsed, and what it shows and hides for that page is applied in the designer.
  • Own form of the editor. When the editor shows its own form, its menus are the real working ones: choosing an item selects it in the tree and, after its handler has run, puts the caret on that handler in the unit.
  • Menus. A click on the menu bar of the form does not open the menu; it selects the menu and the item in the Objects tree.
  • Hint over a component: «Name: Class», with extended hints also place, size, TabStop and TabOrder.
  • Menu wizard (right click → Menu): ready menus (text editor, IDE, browser, ...) and templates *.mnu in the folder MenuTemplates next to the program; items are named by caption (New1, Open1, N1), handlers are created by double click.

3. Which classes are real

  • Delphi components of the pages Standard, Additional, Win32, System, Dialogs, Win 3.1 and Samples are created as real classes (DsgClasses.pas).
  • Stubs. Data Access, BDE, ADO, dbExpress, Internet and a few others (TMediaPlayer, TOleContainer, DDE, TXPManifest, TChart) are read as stubs: a real class with Active/Connected = True in the .dfm would open a connection or a device while the form loads. A visual stub is a grey rectangle with its name, a non-visual one an icon.
  • Third-party components are found in the installed Delphi 7: the known design packages in the registry, the PACKAGEINFO resource of each package (which unit is in which package) and the palette layout of Delphi. Their classes are read from the runtime packages without running their code (BplRtti): ancestors, properties, events. A third-party class can be shown by a similar class of the editor (TComComboBox as TComboBox); such components get a frame of their own colour.
  • Icons of the palette are drawn by code from short scripts (DsgIcons.pas) and smoothed; own icons can be put into palette_icons.txt next to the program.

4. Objects tree and inspector

The tree and the property list come from three sources:

  1. The .dfm of the form. It holds only values that differ from the defaults; full property lists and defaults of VCL classes come from RTTI.
  2. The code of the unit. Components that the code creates (TPanel.Create in FormCreate, helper procedures, creation in a loop, creators through a var parameter) are found by parsing the .pas (BuildCodeRuntime in ObjParse) and shown in the tree and in the designer. They are view only: the designer does not move them and does not write them to the .dfm. Move to .dfm (DfmMove.pas) analyses each of them and moves to the .dfm the ones for which the analysis is sure.
  3. A snapshot of the live form (section 5): what really exists after the code ran, with current values. It is merged over the .dfm data (MergeSnapNode), it does not replace it.

A parsed form is cached in dsgcache\<form>_<crc of the path>.objcache. The key is the checksums and lengths of the form text, the unit text and the snapshot, plus the date of the exe; if it matches, the tree is read from the file without parsing.

5. Snapshot of a live Delphi form

FormSnapshot.pas writes a form that exists at run time as text in the .dfm format, so the inspector reads it with the same parser as a real .dfm. It contains what the .dfm does not: components created in code and the values they have now. It walks the components through RTTI itself instead of WriteComponent: the standard writer reads every published property, including Lines of a TRichEdit line by line through EM_GETLINE, and with RichEdit 4.1 this writes UTF-16 into a one-byte buffer and spoils memory. The unit is self-contained and can be added to any program.

  • Own forms of the editor (the editor edits itself): the snapshot is taken from the live window, when the Objects page is opened and no snapshot exists yet, again when the set of components changed, or by the button.
  • Another project: probe run. unIDE builds a copy of the project, _dsgprobe.dpr next to the real .dpr, with the probe unit DsgProbe. The copy differs in three places: DsgProbe is first in uses; after the last Application.CreateForm it calls DsgProbeDump (snapshot of all created forms to a file, then ExitProcess); Application.Run is not called. So the form constructors and their OnCreate run, but not OnShow, timers, the message loop or OnDestroy. Code that should not run in a probe (looking for a device, long loading) can be put into {$IFNDEF DSGPROBE} ... {$ENDIF}: the copy is built with -DDSGPROBE. The exe and .dcu of the probe go to a temporary folder; the temporary .dpr is deleted after the build. The probe runs once per session with the project; later the button updates it. FormSnapshot.pas is stored in the editor as a resource and written out for the probe.

Live look and .dfm look. The designer can show a form in two ways: with the values of the snapshot (live look) or only with the .dfm values. Two designer forms exist, the visible one and a hidden one of the other look; a property change is copied to the hidden one at once, a larger change (insert, delete, undo) rebuilds it in the background 1.5 s after the edit. For an own form of the editor unIDE compares two texts of the same form: the .dfm compiled into the running exe (the resource TFORM1, TFORM2, ...) and the snapshot. A property where they differ was set by code; in the live look it comes from the snapshot, and the inspector marks it as set by code. Place and size set by code are marked per coordinate (letters L, T, W, H) and can be locked against moving.

6. Rapid-Q forms

A Rapid-Q form exists only as code: CREATE ... END CREATE blocks. The Objects tree shows these blocks as a tree, as the Objects page of RQdebugger does (a CREATE inside another CREATE is its child; one-line CREATE ... : END CREATE is understood; a CREATE without END CREATE is marked).

  • Building the form. From the CREATE nodes unIDE writes a text in the .dfm format (RqDsgBuildDfm) and opens it with its own instance of the same designer. The components in this text are stubs TRqShape that draw themselves by the kind of their Rapid-Q class (button, edit, panel, ...); the kind is the first built-in class in the EXTENDS chain, so QToolBarEX EXTENDS QPANEL is drawn as a panel. Non-visual components (QTIMER, QFILESTREAM, dialogs) are icons; QMAINMENU, QPOPUPMENU and QMENUITEM become VCL menus, so the menu bar looks as in the running program.
  • Classes and properties come from ComponentAll.data: per class its properties (type, access, default, choices such as bsSizeable=2), methods, events and defaults from CONSTRUCTOR. Own components of the program (TYPE ... EXTENDS in the source and its include files) are parsed by RqParseTypes and get the properties of their whole chain. CONST values of the program (RAPIDQ.INC: bsSizeable = 2) turn numbers back into names in the inspector.
  • Value shown (RqDsgValue): a number or a string in quotes from the CREATE block; if the block has an expression or no line for the property, the value from the snapshot (section 7); if there is no snapshot either, the default from the class description.
  • Moving and resizing are written into the CREATE block: the value in the assignment line, or a new assignment in the block. A place or size given by an expression is changed as a number: the line with the expression becomes a comment and the number is written under it (RqReplaceExprLine). The place of the form itself is not changed.
  • Inspector. A property set in the block is changed in the same line (indent, other statements after : and the comment stay); a property not set gets a new line Property = value after the last assignment of the object. Enumerations offer the choices of the class description, colours the cl... constants. Read-only properties, arrays and resources are not edited.
  • Palette. The pages RQ Standard, RQ Additional, RQ System, RQ Dialogs. A click on the form inserts a CREATE block: a visual component into the block of the container under the mouse, before its END CREATE, with Left/Top of the click and the default size of the class; a non-visual one with Parent (QMAINMENU) into the block of the form; other non-visual ones (QTIMER, dialogs) as a separate block before the form.
  • Links. A click on a component selects its node in the tree; a node in the tree selects the component, a node of another form opens that form. After any edit of the text the form is built again, if its .dfm text changed (RqDsgSync).

7. Snapshot of a Rapid-Q program

A value such as Width = MenuPanel.ClientWidth*2\3 cannot be known without running the program. unIDE writes a copy _rqprobe.bas next to the main .bas, builds it into _rqprobe.exe with rc.exe and runs it. The copy has two additions:

  • before the first CREATE of the main part, a timer (DIM ... AS QTIMER, Interval = 1). Windows delivers its message only when the program takes messages from the queue (ShowModal, DoEvents), so by then the main part has run: the objects exist and the expressions are computed;
  • at the end of the file, SUB RqProbeDump: one line Object.Property=value for every readable property of a simple type (by the class description and the TYPE ... EXTENDS chain), then END. The lines are split into SUB RqProbePart1, 2, ...

The values go to _rqprobe.txt: #start right after the timer, #obj Name before each object, #end at the end. From what is in the file unIDE tells how far the program got: no file — it did not reach the timer; only #start — it ended before taking messages; no #end — the last #obj shows where it stopped. The dump waits until the last END CREATE of the main part (RqProbeReady), every 200 ms up to 8 s, then runs as is with #notready. A property that rc.exe refuses to read («Member X not part of class») is left out for all objects of that class, the copy is built again, and the exclusion is kept in dsgprobe\rqprobe_skip.txt. The exe runs in the folder of the .bas, as the real one would (programs take their folder from COMMAND$(0)); QXpTheme.INC restarts the exe once to write its manifest, which is why the exe stays there. Copy, exe and value file stay next to the .bas; _rqprobe_run.bat runs the copy by hand, _rqprobe.trace logs start and dump.

8. Preview in View Form

In the View Unit / View Form window the right panel shows a picture of the form under the mouse. The form is created from its .dfm (properties that would act at load time, such as Active, Connected, Visible, FormStyle, WindowState, Position and ActiveControl, are removed), placed into a hidden host window and painted control by control into a bitmap (VCL controls get WM_ERASEBKGND and WM_PAINT with the bitmap DC, native ones WM_PRINT). The picture is scaled and saved as JPEG in the disk cache with a key from the size and time of the .dfm; a preview from the cache is shown at once, a new one is built 150 ms after the mouse stops.

9. Limits

  • Components created in code are shown, but not moved or written to the .dfm until Move to .dfm moves them.
  • A Delphi snapshot of another project needs a probe build and run (several seconds); OnShow, timers and the message loop do not run in it.
  • A Rapid-Q snapshot needs rc.exe and a program that reaches its message loop; values computed later (in OnShow-like code, timers) are not in it.
  • Rapid-Q components are drawn by stubs, not by the real Rapid-Q controls; objects from $INCLUDE files are not shown in the Objects tree yet.
