Window procedures and callbacks: rc.exe and the FreeBASIC build

Rapid-Q side: chapter 11, inc/NewWndProc.Inc, inc/CallBack_0.Inc … CallBack_8.Inc, inc/CallBackForwarder.Inc, inc/rapidq2.inc. FreeBASIC side (unIDE, RqToFb): RqLcl/tofb/RqToFb.pas, RqLcl/inc/rqrt.bi (RqSetWndProc), RqLcl/dll/rqlclwnd.pas (event WndProc), rules in RqLcl/RAPIDQ_RULES.md, «Function pointers».

1. What Rapid-Q offers

  • BIND variable TO procedure stores in a numeric variable a value for the procedure and binds the number of its parameters (the template). CALLFUNC (variable, arguments) calls it. A function pointer cannot be passed as an argument (chapter 11).
  • CODEPTR (procedure) (also CALLBACK) gives an address «for CALLBACK procedures». The documentation adds: «Not all cases are implemented, results may vary depending on the CALLBACK and the type of parameters it receives». Nothing more is said about the limit.
  • The event WndProc SUB (Hwnd%, Msg%, wParam%, lParam%) exists only for QFORM, QEDIT, QLABEL and QLISTBOX. For QFORM the documentation says: «Only one WndProc per Form is allowed. So if you have multiple forms, only one may be able to receive messages at a time. (Future consideration to correct this)». In RQdebugger and its include files WndProc = occurs only in lines that are commented out.

So a program that wants to see the messages of another control (WM_PAINT of a QRICHEDIT, keys of a QSTRINGGRID) or of several forms has to give Windows a window procedure of its own with SetWindowLong(hWnd, GWL_WNDPROC, address) — and Rapid-Q does not give it a reliable address of a procedure for that.

2. The trick in NewWndProc.Inc and CallBack_N.Inc

The include files of the user (authors in the files: Jacques, JohnK, Paul, Warriant; 2005–2006) work around it with machine code built at run time:

  1. For each number of parameters there is one master function, for example MasterCallBack_4 (hFunction, Arg1, Arg2, Arg3, Arg4). Its address is taken once with CODEPTR: DefInt lpCallBack_4 = CodePtr(MasterCallBack_4). Inside, it binds a variable to the template FuncBind_4, assigns hFunction to it and calls CALLFUNC(hBind, Arg1, Arg2, Arg3, Arg4) — that is, the procedure of the program.
  2. For each window (each callback) the program allocates 14 bytes on the process heap (HeapAlloc) and writes x86 code into them through a QMEMORYSTREAM and MEMCPY: 
    58                 pop  eax          ; return address
68 xx xx xx xx     push hFunction    ; the procedure bound with BIND
50                 push eax          ; return address back
B8 xx xx xx xx     mov  eax, lpCallBack_4
FF E0              jmp  eax
    When Windows calls this piece of code with (hWnd, uMsg, wParam, lParam), the master function receives one more first argument — hFunction — and passes the four others on to the procedure of the program.
  3. SetNewWndProc(ObjectHandle, hFunction) (NewWndProc.Inc) builds such a forwarder and gives it to SetWindowLong(hWnd, -4, forwarder); the result is the old window procedure, which the new one calls with CallWindowProc. SetNewCallBack_N(hFunction) and SetNewFwToCallBack(ForwardTo, hFunction) return the forwarder for other callbacks (SetTimer, EnumChildWindows, ...).

Use in RQdebugger:

DefInt iTmpBind
Bind iTmpBind To RichEditWndProc
OldRichEditWndProc = SetNewWndProc (SrcEdit.Handle, iTmpBind)
...
FUNCTION RichEditWndProc (hWnd AS LONG, uMsg AS LONG, wParam AS LONG, lParam AS LONG) AS LONG
  if NoPaint=1 and uMsg=WM_PAINT then exit function
  Result = CallWindowProc(OldRichEditWndProc, hWnd, uMsg, wParam, lParam)
END FUNCTION

3. The limits of the trick

  • CODEPTR itself. The trick exists because CODEPTR does not give a usable address in every case; only one CODEPTR per number of parameters is taken, for the master function. The comments of the include files point at the problem without describing it: «If you use threading you cannot include another CodePtr(SUB), address is used up» (QProgress.inc), «correct codeptr bug by redirecting window messaging» (rapidq2.inc), «Win9x bug» solved by a rewritten forwarder (CallBack_4.Inc). What exactly the limit is, was not found out.
  • Fixed numbers of parameters. A separate include and master function for 0 … 8 parameters (CallBack_0 … CallBack_8).
  • Machine code in data memory. The forwarder lies in memory from HeapAlloc. Windows with Data Execution Prevention for the program may refuse to execute such memory; whether it happens on the user's computers was not checked.
  • 32-bit x86 only, and the 14 bytes per window are never freed.
  • Methods of own components are also used this way in rapidq2.inc (BIND This.BindIndex TO This.WindowProc, CODEPTR(This.EnumChild)).

4. What the FreeBASIC build does instead

In FreeBASIC a SUB or FUNCTION of the translated program is compiled to native code with the stdcall convention and parameters by value, which is what Windows expects from a window procedure or a callback. Its address can be given to Windows as is. RqToFb therefore translates (since commit ede0410):

Rapid-QFreeBASIC
CODEPTR(Proc), CALLBACK(Proc)Cast(Integer, @Proc)
BIND v TO Procv = Cast(Integer, @Proc), and the template of v is remembered (collected in the first pass, so CALLFUNC may stand before BIND in the text)
CALLFUNC(v, a, b)Cast(Function(parameters of Proc) As type, Cast(Integer, v))(a, b) — a direct call through a typed pointer
SetNewWndProc (NewWndProc.Inc)body replaced by RqSetWndProc: SetWindowLongA (SetWindowLongPtrA in 64 bit) with the address itself; the x86 code is not built (the old body stays in the output as a comment)
SetNewCallBack_0 … 8, SetNewFwToCallBackreturn the address itself
Object.WndProc = Procthe event WndProc of QFORM, QEDIT, QLISTBOX, QLABEL in RqLcl: the window procedure of the control is subclassed in the DLL, the handler gets every message before LCL, including WM_COPYDATA and WM_USER+ messages

The program text stays as it is: in RQdebugger the lines with $INCLUDE "NewWndProc.inc", Bind iTmpBind To RichEditWndProc and SetNewWndProc(SrcEdit.Handle, iTmpBind) are translated and compiled without changes to the source (the rich edit and two grids are subclassed this way).

What this removes:

  • no machine code at run time, no HeapAlloc, nothing that DEP could refuse;
  • any number of window procedures and callbacks, with any number of parameters — no master function per parameter count;
  • no CODEPTR limit: every procedure has its own real address;
  • a window procedure of QFORM, QEDIT, QLISTBOX, QLABEL can be given without any API call, with Object.WndProc = Proc; RqLcl subclasses each window separately, so every form has its own (several forms at once were not tested).

Checked with the tests (Wine, fbc 1.10.1, 32 bit): tests/funcptr.bas — the examples of chapter 11 (BIND/CALLFUNC as statement and function, arrays of pointers, the template from 11.4), CODEPTR in SetWindowLong (500 messages through the new window procedure with CallWindowProc) and in EnumChildWindows, a list subclassed exactly as in RQdebugger through NewWndProc.Inc, SetNewCallBack_4 for SetTimer; tests/wndproc.bas — the WndProc event of QFORM, QEDIT, QLISTBOX, QLABEL, also after the form window is recreated by LCL.

5. What is still limited

  • 64 bit. Rapid-Q programs keep addresses in LONG variables. In a 64-bit program an address does not fit in LONG (fbc refuses Dim Shared lp As Long = Cast(Integer, @Proc)), so BIND, CODEPTR and SetNewWndProc work in the 32-bit build only.
  • Methods of own components in BIND and CODEPTR (rapidq2.inc, RapidFRM.inc) are a translation error: a method of a FreeBASIC Type has a hidden parameter This, which Windows does not pass.
  • The procedure must have the parameters Windows passes (for a window procedure four LONG values). In Rapid-Q only their number mattered for the template.

6. Later: syntax extensions for the FreeBASIC build

The FreeBASIC build can understand more than rc.exe. Extensions of the Rapid-Q syntax that use what FreeBASIC has are possible; none of them is made yet, and each needs a decision. Such a source would no longer compile with rc.exe, so an extension would be switched on per file, for example with a comment line like the existing '$RQFB SMART (rc.exe skips comments). Candidates:

  • An address type (for example AS PTRINT, an integer of pointer size) for BIND, CODEPTR, VARPTR, Mem.Pointer and handles, so that the same program also builds in 64 bit.
  • Methods as callbacks through a generated forwarder procedure (as is already done for event handlers of own components), so that CODEPTR(This.EnumChild) becomes possible.
  • Function pointers as parameters and typed procedure variables (AS SUB (LONG, LONG)), which chapter 11 says Rapid-Q cannot do.
  • Calling convention on DECLARE SUB/FUNCTION (CDECL for C callbacks such as qsort).
  • FreeBASIC headers (#include "windows.bi") instead of hand-written DECLARE ... LIB, and a block of FreeBASIC code passed through unchanged.
  • Language features: optional parameters with default values, overloading, threads (ThreadCreate, MutexCreate), WSTRING.
